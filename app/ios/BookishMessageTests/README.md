# Message model checks

Run `sh app/ios/BookishMessageTests/run-model-tests.sh` from the repository root. These tests require Foundation and `swiftc`, and they do not require an iOS simulator or a Messages account. `SWIFTC=/path/to/swiftc` selects a standalone toolchain if the system toolchain is unavailable. Temporary binaries are removed when the runner exits.

The message URL contains the complete card, including names and responses shared by members. People who receive the message in the transcript receive this data. Base64 encoding is not encryption. State stays in the fragment of `https://meetbookish.com/imessage/v1#payload=...`, which browsers do not send in HTTP requests. There is no interactive Mac fallback. The model does not upload data, discover real names, authenticate identities, or send messages.

Merging combines responses only when the card identifier and all card metadata agree. The newest timestamp wins for each participant, and an equal timestamp preserves the local response. Cards hold at most 40 members, but Apple's 5,000-character message URL limit can fill a card sooner, depending on names and identifiers. Encoding rejects an oversized snapshot before insertion. If a combined snapshot would exceed the member limit, existing local members stay, and additional members are admitted in name and identifier order until the card is full. Display order uses names and identifiers, never page progress, RSVP choice, or vote totals. A message can contain an older snapshot, so participants should reopen the latest card when responding.

Server cards use a separate v2 resource route, `https://meetbookish.com/imessage/v2/{take|vote|meeting}/{uuid}`. Only the kind and UUID appear in that URL. The app's signed-in client fetches `bookish_message_card`, then calls `BookishMessages.share({card})`. Native decoding rebuilds a bounded allowlist before drawing an actual `MSMessage` in Apple's message composer. Tea images contain an anonymous header, a page or DNF marker, decorative sealed lines, and no body pixels. Vote images use aggregate tallies and bundled public book titles and covers, with neutral labels for books outside that catalog. Meeting images contain aggregate RSVP counts and open bring items, without an address or claimant identity. No session is sent to, or stored by, the Messages extension.

The extension opens `bookish://message/{kind}/{uuid}` for v2 cards. The main app must handle both cold and warm URL opens, require a reader session, and request fresh authorized resource data. Tea must stay sealed until the feed returns an allowed body. The extension does not reveal on tap. Existing v1 RSVP, vote, bookmark, draft, merge, and sticker behavior remains available.

`BookishMessages.share` resolves `{status:'sent'|'cancelled'|'failed'}` after the native composer finishes. A device without Messages rejects with `UNAVAILABLE`. A simultaneous native share rejects with `BUSY`. `BookishMessages.saveCalendar({content,fileName})` accepts the signed-in calendar endpoint's ICS text, presents Apple's file share sheet, and resolves `{status:'shared'|'cancelled'}`. Native uses the fixed filename `bookish-meeting.ics`, bounds content to 1 MiB, writes into a unique protected temporary directory, and removes that directory when sharing finishes. The caller must not put a session into a URL or the ICS.

Native delivery, recipient-side extension association, cancellation, app installation fallback, and calendar import require a signed-in physical-device check. An isolated renderer screenshot verifies card art only, without claiming to show a real Messages conversation or server authorization.
